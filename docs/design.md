# Design

How the classifier is built. This document grows with each task of the [roadmap](roadmap.md).

## Architecture

Hexagonal (ports and adapters) inside a single Maven module, under the base package `com.ebravo.taxclassifier`:

| Package | Responsibility | May depend on |
|---|---|---|
| `domain` | Products, tax classification and the rules around them | The JDK core only |
| `application` | Use cases that drive the domain through ports | `domain` and the JDK core only |
| `adapter` | Kafka, the official calculator over HTTP, the Claude API | `application`, `domain` |

Dependencies point inward. `ArchitectureTest` enforces the rules on the production code, and `ArchitectureRulesTest` proves each rule fires on test fixtures that break it.

## Technology

- Java 25, Spring Boot 4.1.
- Maven through the Maven Wrapper.
- Spring Kafka on Apache Kafka 4.2 (KRaft); Jackson 3 for JSON.
- Spring's `RestClient` for the official calculator.
- PostgreSQL 18.7 through Spring's `JdbcClient` for the AI's suggestions.
- The Anthropic Java SDK (`anthropic-java` 3.7.0) for the Claude API.
- JUnit, AssertJ, ArchUnit, JaCoCo, PIT (mutation testing), Testcontainers (a real Kafka broker and PostgreSQL in tests), `MockRestServiceServer` (recorded calculator responses in tests), the JDK's `HttpServer` (stubs of the Claude API, and of a calculator that does not answer, in tests).

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Single Maven module, layering enforced by ArchUnit whitelists | Keeps the build simple. A whitelist also keeps out libraries nobody thought to forbid: Spring, Kafka, HTTP clients, the Claude SDK. The JDK core is `java.lang`, `java.util`, `java.math` and `java.time`; I/O, networking and SQL belong to adapters. Patterns are anchored to the base package, so a library's own `domain` package does not pass as ours. |
| D2 | 100% line, branch and mutation coverage on `domain` and `application`, enforced in `verify` | The tax rules decide what reaches an accountant for review; every rule is exercised, and PIT checks the tests would notice it break. Adapters are tested only where they hold behavior of this service. |
| D3 | Dependencies pinned to releases published at least two weeks earlier | A fresh release has had no time to show its regressions. Spring Boot 4.1.2 was chosen over 4.2.0 and 4.1.3, both published on 2026-11-19. CI actions are pinned to exact releases, and the Maven Wrapper checks the SHA-256 of the Maven it downloads. |
| D4 | The official calculator runs as a separate process, pinned at tag `1.6.1` (commit `150cccb`, database `V0059`) and built on JDK 25 | Its code stays out of this repository, and a fixed release keeps the recorded responses valid. `1.6.1` was released on 2026-10-27 (commit of 2026-10-22); `1.7.2` came out on 2026-11-19, too recent under D3. The tag declares Java 21; on JDK 25 it builds with `-Dmaven.compiler.proc=full`, because JDK 23 stopped running annotation processors such as Lombok by default. One JDK serves both projects. |
| D5 | The AI chooses from the full official CBS/IBS list of CST and `cClassTrib` for the date; the calculator checks the link to the NCM | Release `1.6.1` lists `cClassTrib` by CST, date, NBS or actor, never by NCM (18 CSTs and 164 `cClassTrib` for CBS/IBS on 2027-03-10). The Imposto Seletivo lists are separate endpoints and stay out, as the scope calculates CBS and IBS only. An NCM can only be checked against one `cClassTrib` at a time, through `GET /dados-abertos/classificacoes-tributarias/ncm-aplicavel` or the `REG-011` error of the calculation. An unlinked choice comes back as `INCONSISTENCIA_ENTRADA` with `REG-011` and goes to review. |
| D6 | The domain reads the products CSV from lines already read; every data line becomes a product or a rejection with its line number and reason | The domain stays free of I/O (D1); the publish command of task 03b reads the file. The header is `code;description;ncm;price`, fields are split on `;` and kept as written, the code has no surrounding spaces (it is the product's identity, so it is rejected, never trimmed), the NCM has 8 digits and the price is a positive decimal with at most 2 places. A price is kept at scale 2 with `RoundingMode.UNNECESSARY`, so it is never rounded: a third decimal rejects the line. A missing or wrong header rejects line 1 and every data line, since the columns cannot be trusted. A repeated code is not an error: it is an update of the same product. |
| D7 | Products are published to `produtos` keyed by product code, as JSON with the price as a string, with `acks=all` and idempotence | The key sends every update of a product to the same partition, the only place Kafka keeps order, so a product's updates are classified in order (scenario 5). The value is `{"code","description","ncm","price"}` with the price as written at scale 2 (`"25.90"`): a JSON number would let a consumer read it as a double. No Jackson type header: the contract is the JSON alone. The topic has 3 partitions, room for the two consumer instances of the rebalance scenario, and one replica on the single local broker. `acks=all` and `enable.idempotence=true` are kafka-clients defaults, set explicitly so a conflicting setting makes the producer fail at start. The publisher sends every product before waiting for any; a failure part way leaves earlier products published, which is safe because publishing again is an update under the same key. |
| D8 | `java -jar target/tax-classifier.jar publish <file>` publishes a products CSV and answers with its exit code: 0 every line published, 1 the valid lines published and some rejected, 2 nothing guaranteed published | A script or CI job can tell a catalog with errors from a publish that did not happen. Each rejected line goes to stderr as `line N: <reason>`, a one-line summary to stdout, and a failure (missing file, a file that is not UTF-8, the broker unreachable, no file given) to stderr as one `publish failed: <reason>` line, with the root cause of a Kafka error. The file is read strictly as UTF-8 and a leading byte order mark, which Excel writes, is removed. Without the `publish` argument the application runs as the classification service (D15); options may come before it. The command runs in the `publish` profile, which leaves the classification listener out, so publishing never calls the AI. stdout holds the summary only: in that profile the banner is off and logs below WARN are dropped, the Kafka client's below ERROR and Spring Kafka's entirely, since the command reports a Kafka failure itself. The admin operation and `max.block.ms` wait 10 s each, so an unreachable broker is reported in about 30 s (34 s measured) instead of 106 s. |
| D9 | The `OfficialCandidates` port returns, for a date, the official CBS/IBS CSTs each with its `cClassTrib`, read from `GET /dados-abertos/situacoes-tributarias/cbs-ibs?data=`; an error is thrown, never returned as an empty list | The list keeps the calculator's nesting, so each CST description is kept once and task 05 checks a suggestion against it in the domain. `TaxSituation` copies its list, so the official list cannot change after it is read. The calculator's internal `id` stays in the adapter. An empty list is a real answer, for a date before the tables start (`[]` for 2020-01-01); an error turned into one would leave the AI nothing to choose from and hide the failure, so a 4xx or 5xx surfaces as a `RestClientResponseException` with the status. The calculator is found at `calculator.base-url`. The contract test replays responses recorded from release `1.6.1` through `MockRestServiceServer`, which needs no extra library; a calculator that does not answer or refuses the connection is tested against the JDK's `HttpServer` (D23). |
| D10 | `SuggestionCheck` accepts an AI suggestion only when its `cClassTrib` is listed under the CST it names and its confidence reaches the threshold; otherwise it sends it to review with one reason, `OUTSIDE_OFFICIAL_LIST` before `LOW_CONFIDENCE` | The AI writes both codes, so a real `cClassTrib` under the wrong CST is an inconsistent answer, not a match; in the list of release `1.6.1` every `cClassTrib` sits under one CST only. A confidence equal to the threshold is accepted. Confidence and threshold are `BigDecimal` from 0 to 1 compared with `compareTo`, so `0.8` equals `0.80` and the boundary has no floating-point error; a null or out-of-range value is rejected when built, so a threshold misread as `80` cannot send every suggestion to review in silence. A null or blank CST or `cClassTrib` is rejected too, so a malformed answer is never reviewed as an unofficial code, and a review always carries its reason. The threshold is a constructor argument, set from configuration in task 07b. A suggestion outside the list is reviewed for that reason even when its confidence is also low, since no confidence makes an unofficial code acceptable. |
| D11 | The `AiAdvisor` port asks `claude-haiku-5-5`, through the official SDK with its retries off, for a CST, a `cClassTrib`, a justification and a confidence, as JSON in a schema generated from a record; the official list goes in a cached system block, and the product's description and NCM in the user message as a JSON object | Haiku is enough to choose from a closed list, and structured output makes the answer parse or fail, never half-read; the confidence is read as a `BigDecimal` from the JSON. The list is the same for every product of a date, so its system block is cached. The product text is data from the catalog, so it goes in the user message as a JSON object, where no text in the description can pose as another field, and the instructions say it is never an instruction; its code and price say nothing about its classification and stay out. The justification is in Brazilian Portuguese for the accountant, and a blank one is rejected like a blank code. Effort is set to medium, the model's default, so a model change cannot shift it; `max_tokens` is 16000 because adaptive thinking spends from the same budget as the answer. The AI does not write the legal basis: an article it invents would read like a real one, so the basis comes from the calculator by `cClassTrib` (task 06c). The SDK's two automatic retries are turned off, since retry is a behavior of the classification flow (task 12b). SDK 3.7.0 sends the key as `Authorization: Bearer`. The manual checklist of task 06a, run against the real API, confirmed that it accepts the request, the generated schema and the key, and that the second product read the official list from the cache (7,744 tokens). |
| D12 | The `AiAdvisor` port fails with `AiFailure`, whose kind says why no suggestion came back: `REFUSED`, `TRUNCATED`, `MALFORMED`, or `HTTP_ERROR` with the status | The classification flow must never take a failed answer for a suggestion, and task 12b must tell what to retry without the SDK's types: the status separates a 429 or a 5xx from a 401. The stop reason is read before the text, since a refusal comes back as HTTP 200 with no text or text off the schema. Only `end_turn` is a finished answer, as the request has no tools and no stop sequences. `max_tokens` and `model_context_window_exceeded` are `TRUNCATED`; any other reason, or none, means the answer is not what was asked for and is `MALFORMED` with the raw value, so task 12b never takes it for a cut-short answer. A response that is not a message (a proxy's HTML page), a finished answer with no text block, text that does not parse into the schema, or values the domain rejects is `MALFORMED`, with its cause. The failure is Serializable, so it keeps the status as an `Integer`. A test counts the requests the stub receives, so dropping `maxRetries(0)` (3 requests on a 429) fails the build. A call that never gets an answer (no connection, timeout) is `NO_ANSWER` (D23). |
| D13 | The `OfficialLegalBasis` port returns, for a `cClassTrib` and a date, its official legal basis (the short citation such as `Art. 11, VIII`, the full text of the article and the normative reference) as the calculator publishes it, from `GET /dados-abertos/fundamentacoes-legais?data=`; empty when none is published, and an error is thrown, never returned as empty | Release `1.6.1` lists the legal bases by date only (161 on 2027-03-10), so the adapter reads the list for the date and picks the code. Three `cClassTrib` of the official list (220001, 220002, 220003) have no legal basis, so a missing one is an official answer and the classification flow decides what to do with it (D14); an error turned into one would hide a failed calculator behind that answer. The texts keep the calculator's literal `\n` (a backslash and an n): official text is never rewritten, and whoever displays it decides. The CST, the descriptions and the tax set (always `CBS e IBS`) stay in the adapter, since the official list already carries them. The calculator itself assumes one legal basis per code and date, and so does the adapter. A null code is a caller's bug and is rejected before the request. A date with no official tables (`[]`, as for 2020-01-01) also gives empty for every code; the flow never gets there, because the official list for that date is empty too and no suggestion can match it (D10). The list is read once per date (D16). |
| D14 | `ClassifyProduct` reads the official list for the day in São Paulo, asks the AI unless the product's suggestion is saved (D22), checks the answer (D10) and, only for an accepted suggestion, calculates CBS and IBS (D19) and reads the official legal basis (D13) for the same day; the outcome is `Classified` with the legal basis, empty when none is published, and the calculation, or `ToReview` with the reason and the calculator's errors | The official tables are dated by the Brazilian calendar, so the day is the clock's instant in `America/Sao_Paulo`, whatever zone the clock runs in: at 23:59:59 in São Paulo the list is still that day's. An accepted `cClassTrib` with no published legal basis (220001, 220002 and 220003 in release `1.6.1`) is classified without one: the missing basis is the official answer, not doubt from the AI, and review is kept for what the machine could not decide. A suggestion sent to review skips the calculation and the legal basis, which only matter for a classification that stands. The outcome leaves out the product, which the caller already holds. A failure of the AI or the calculator propagates: retry is task 12b and review after a permanent failure is task 13. An empty official list still reaches the AI, and its answer goes to review as outside the list; the calculator answers one only for a day before its tables start (2020-01-01), which a correct clock never gives. The official list and the legal bases are read once per date (D16). |
| D15 | Without the `publish` argument the application is the classification service: the group `tax-classifier` consumes `produtos` one record per poll from the earliest offset, runs `ClassifyProduct` (D14) with the threshold from `classification.confidence-threshold` (0.80), and publishes to `produtos-classificados` or `produtos-revisao`, keyed by product code, committing each offset after its result is sent (D20); a failure is tried once and skipped until task 12b | A product published before the service first starts is still classified, so the group starts from the earliest offset. Both output topics carry the product as it was consumed (D7) and the suggestion, with the confidence as a string like the price: the accountant sees what was classified without joining on the key. A classification adds `legalBasis`, `null` when none is published (D14), and `calculation` with `base`, `cbs` and `ibs` as strings and `simulated` (D19); a review adds `reason` and `errors`, the calculator's `code` and `detail` of each, empty when the check sent it to review. 3 partitions each, like `produtos`, so a product's results keep their order. The listener waits for its send, so a failed send reaches the error handler instead of hiding behind a committed offset. Spring Kafka's default error handler tries a failed record 10 times with no backoff, each one a paid call to the AI (measured in a test); until task 12b decides the retry, a failure is logged and skipped, and the product stays unclassified until task 13 sends it to review. A record that is not a product's JSON failed inside the consumer's poll, before the error handler: by hand it stalled its partition and logged 1.5 GB in 45 s, so `ErrorHandlingDeserializer` hands it to the error handler, which skips it like any other failure. One record per poll keeps a poll far below `max.poll.interval.ms` (5 min), since each record waits on the AI; a poll of 500 could outlast it, leave the group and classify the same records again. The broker fetch is still batched. The 0.80 threshold is uncalibrated (see the trade-off "AI confidence"). |
| D16 | Each calculator adapter keeps the answer of the last date it read, the official list or the date's whole list of legal bases; another date replaces it, and a read that fails or comes back with no body keeps nothing | The calculator answers the same lists all day, so each product made two requests for data already in hand. The clock only moves forward, so a date that is replaced is never asked again: one entry is the whole cache, with no size limit or expiry to tune. The legal bases are kept as the date's list and each code is picked from it on every call, since the calculator lists them by date only (D13). A failure is never kept, so a calculator that fails once is asked again on the next product instead of failing the rest of the day; a response with no body counts as a failure. Any other answer is kept for the day, an empty list included: release `1.6.1` was seen answering `[]` only for a date before its tables (D9), so an empty answer for a covered date is not guarded, and a restart clears it. No lock: the listener has one thread, and two threads missing at once would only repeat a request. The cache is written by hand in about 20 lines, as Spring's cache abstraction would need Caffeine and its configuration to hold only the latest date. A calculator updated during the day is seen on the next date or restart (see the trade-off "Official list freshness"). |
| D17 | The `TaxCalculator` port calculates CBS and IBS for a product under its suggested CST and `cClassTrib` at an instant, through `POST /observabilidade/regime-geral`, as one item of an operation in the municipality from configuration; the result has one case per `estadoItem`: `Calculated` with the base, CBS and IBS and whether it is simulated, or `InputInconsistency`, `NotImplemented` or `TechnicalFailure` with the calculator's errors | The calculator answers HTTP 200 for an item it could not calculate, so the state decides the case, never the status. `CALCULADO` and `CALCULO_SIMULADO` carry the same amounts; release `1.6.1` answers the second only when the caller sent nominal rates (`ObservabilidadeService`), so a flag tells the accountant the rates were not the law's. Each error keeps its code and detail: the code tells the accountant why the item went to review (D19), `REG-011` among them, and the type, title and pointer add nothing. The state is read into an enum, so a state a later release adds fails the parse instead of passing for a result. The taxable event is the instant in `America/Sao_Paulo`, the zone of the official list's day (D14), which gives `-03:00`: an instant at 02:30 UTC is still the previous day in both. It is cut to whole seconds, since release `1.6.1` reads `dhFatoGerador` as `yyyy-MM-dd'T'HH:mm:ssXXX` and answers HTTP 400 for the fractions the system clock carries (seen in the manual checklist of task 09); cut, not rounded, so 23:59:59.9 never moves to the next day. The request carries the product code as the operation id, the NCM, the codes and the price as the base; the CSV has no location, so the municipality and UF come from `calculator.municipality` and `calculator.uf` (São Paulo, `3550308`/`SP`). Before 2027 the calculator resolves the rates and forbids sending them; from 2027-01-01 it requires them, or every item comes back `INCONSISTENCIA_ENTRADA` with `REG-037` (measured), so the request carries them from then on (D18). An operation rejected as a whole, such as an unknown municipality (`REG-019`), comes back as 422 and surfaces as a `RestClientResponseException`, like D9. The amounts are read from the operation's total, which with one item is the item's own: release `1.6.1` answers `CALCULADO` for an immunity (CST 410, measured for 410001, 410004 and 410999) with no amounts on the item, and totals it at 0.00. A missing amount is rejected when the result is built, so a classification never carries a null CBS. The amounts keep the calculator's scale (2) and rounding. Release `1.6.1` answers `FALHA_TECNICA` (CAL-001 to CAL-012) for data missing from its own database, such as a rate not found; no valid input produced one, so its contract test uses a response written in the recorded shape. |
| D18 | From 2027-01-01, every calculation request carries the nominal CBS, state IBS and municipal IBS rates of `calculator.nominal-rates`, in percent (8.8, 0.05 and 0.05 by default, the official example's values); before that date it carries none | Release `1.6.1` holds reference rates for 2026 only: it forbids sending rates before 2027 (`REG-036`) and requires them from then on (`REG-037`), both measured, and answers `CALCULO_SIMULADO` when they are sent, which D17 flags. The year is the taxable event's in `America/Sao_Paulo`, the date the request carries: the calculator reads the year from that local date, so 02:59:59 UTC on 2027-01-01 is still 2026 for both. One set of rates serves every year from 2027 on, since the calculator accepts any (measured for 2029) and the law's rates for 2027 are not yet set. The rates go for every CST: one with no CBS/IBS group, such as an immunity (410001), does not require them but accepts them and comes back `CALCULO_SIMULADO` at 0.00 (measured), and release `1.6.1` keeps which CST has the group (`inGrupoIbsCbs`) in its database, published by no endpoint. The amounts are the calculator's: with 0.05 and 0.05 on 25.90 it answers 0.01 for each IBS share and 0.03 for the IBS, rounded on the total rate, and the adapter reads the total (D17). |
| D19 | `ClassifyProduct` routes an accepted suggestion by the calculator's `estadoItem` (D17): `CALCULADO` and `CALCULO_SIMULADO` are classified with the amounts and the simulated flag; `INCONSISTENCIA_ENTRADA` goes to review as `INPUT_INCONSISTENCY` and `NAO_IMPLEMENTADO` as `NOT_IMPLEMENTED`, each with the calculator's errors; `FALHA_TECNICA` throws `CalculationFailed`, never a review | Scope routes only a calculated item to `produtos-classificados`. An inconsistency, such as `REG-011` for a `cClassTrib` not linked to the NCM (scenario 4), and a `cClassTrib` the calculator does not yet handle (`CAL-007` for 620001 in release `1.6.1`) give the same answer when asked again, so the accountant decides. `REG-036` and `REG-037` are errors of this service's request, not of the AI, but they take the same path as any inconsistency: one rule with no codes listed in the flow, and from task 08b no request should get them. `FALHA_TECNICA` is the calculator failing on its own data, not a doubt about the classification, so it fails like any other calculator failure: logged and skipped until task 12b decides its retry and task 13 sends an exhausted one to review. Its errors go in the message only, as `CalculationError` is not Serializable and the domain stays free of `java.io` (D1). The clock is read once, so the official list's day and the taxable event are the same instant, and the legal basis is read only for a calculated suggestion. The switch over the result has no default, so a state a later release adds must be routed before the code compiles. |
| D20 | The classification service commits each record's offset on its own (`ack-mode: record`), synchronously, once the listener returns, which is after its result is sent; a product whose service dies before publishing is classified again when the service comes back | Committing after the result is published means no product is lost: one in flight when the service dies is read again from the committed offset. The commit is manual in the Kafka client's sense: the client's auto-commit is off and the listener container commits, not a timer. Spring Kafka 4.1.2 already turns off auto-commit and commits after the listener returns (batch mode), and the listener waits for its send (D15), so the tests that prove it passed on their first run; record mode states it and bounds what a crash reprocesses to the one product in flight, whatever the poll size, where batch mode would reprocess every record of the poll. `MANUAL_IMMEDIATE` acknowledgement was turned down: a branch that forgot to acknowledge would stall the commit, and the error handler's skip would no longer commit the skipped record (in the 4.1.2 source only `MANUAL` commits a recovered record). The test throws an `Error` before publishing, as a fatal error such as `OutOfMemoryError` would: it stops the consumer without committing. With `enable.auto.commit=true` the same test loses the product, as closing the consumer commits its position (measured); a `kill -9` is checked by hand (`docs/failure-scenarios.md`). The delivery is at least once: a death between the send and the commit publishes the result again, though the AI is not paid again (D22; see the trade-off "At-least-once"). |
| D21 | The `SuggestionStore` port keeps the AI's suggestion per product, keyed by its code and a SHA-256 of its NCM and description, in the PostgreSQL table `ai_suggestions`; a second save under the same key keeps the first; `schema.sql` creates the table on start, and the publish command never touches the database | A duplicate must not pay for the AI again (scenario 1, task 11b), and the AI's answer depends on the description and NCM only (D11), so the price is left out: a price update finds the suggestion and is still calculated on its own price. The code stays in the key, as it is the product's identity (D6). The hash input is the NCM's length, the NCM and the description, so no two pairs match even for a record on `produtos` whose NCM skipped the CSV's 8-digit check (D6), and a missing NCM or description is rejected instead of being hashed as the text `null`. The text is hashed as received, never normalized, like the official texts (D13): a description saved once precomposed and once decomposed asks the AI twice. The hash keeps the key at 64 characters whatever the description's length, and it is computed in the adapter, since `java.security` is outside the domain (D1). PostgreSQL survives a restart and is shared by the two instances of task 15, so a product moved by a rebalance is not paid for again; an H2 file would be one per instance, and H2 in memory would lose the suggestions in a crash. The confidence is `numeric`, which keeps its scale: `0.90` comes back as `0.90`. The insert is `ON CONFLICT DO NOTHING`: two instances classifying one product at once, which only a rebalance allows, both pay for the AI and the first answer stays for both (D22). One table needs no migration tool: `CREATE TABLE IF NOT EXISTS` runs on every start (`spring.sql.init.mode: always`), and Flyway was turned down (see the trade-off "Schema management"). The publish profile turns the init off and the pool connects on first use, so publishing runs without PostgreSQL: the publisher's test, which starts no database, fails to start with the init on. The image is `postgres:18.7` (tagged on 2026-11-09, D3), with no volume, like the broker. |
| D22 | `ClassifyProduct` looks up the product's saved suggestion (D21) before asking the AI; a new answer is saved as soon as the AI returns, before it is checked or calculated, whether it is accepted or sent to review, and the classification goes on with the suggestion the store kept; a saved suggestion is checked against the official list of the day, calculated on the product's own price and published again | A duplicate pays for the AI once (scenario 1). Saving before the calculation covers the crash of D20: a service that dies after the AI answers and before publishing reads the product again and finds its suggestion, so the crash test of task 10 now asks the AI once. Skipping a repeated message was turned down: a death between publishing and saving would pay for the AI again, and a product whose price alone changed would be dropped instead of calculated on its new price. The repeat is checked again because the official list is read by day, so a code that left the list goes to review instead of standing (see the trade-off "Stored suggestion age"). A suggestion sent to review is saved too: the same input gets the same answer, and the accountant decides on it. Going on with the kept suggestion, not the one in hand, covers two instances that both missed the store (D21): the one that lost the insert publishes the winner's answer, so the output topics never hold two answers for one input. A failed AI call saves nothing, so the product is asked again. A failure of the store propagates like any other until task 12b, even after the AI answered, so the product is skipped and its next read pays for the AI again: the application layer cannot tell a database error from a bug, and a classification that went on without saving would lose the protection while nobody notices. The listener test publishes a product twice and once more at a new price: the AI is asked once, and the third result is calculated on the new price; with a store that never finds a suggestion, the same test asks the AI three times. |
| D23 | The calculator ports fail with `CalculatorUnavailable` when the calculator does not answer within the timeouts (`spring.http.clients`, 2 s to connect and 10 s to read), refuses the connection or answers 5xx; the AI port fails with `AiFailure` `NO_ANSWER` when Claude does not answer within `ai.timeout` (60 s) or refuses the connection | A calculator with no timeout held the consumer for as long as it hung, and the Claude SDK waited up to its default of 10 minutes; both failures reached the flow as library types, so the retry of task 12b could not tell them from a bug. These are the failures that asking again may cure. A 4xx, such as a 422 for an operation rejected as a whole (D17), and an answer that does not parse stay as they were: asked again, the calculator gives the same answer. One helper in the calculator adapter translates for the three adapters, around the request and the read of its body, since a read timeout can fire while the body is read; an interceptor would see only the headers. The timeouts are Spring Boot's settings for HTTP clients, which only the calculator's `RestClient` uses (Claude's SDK has its own client). The SDK's retries stay off (D11), so a call with no answer is sent once, which a test counts. The tests that need no answer at all run against the JDK's `HttpServer`, holding the response or on a port with no listener, since `MockRestServiceServer` can only answer; the `RestClient` test slice leaves out the HTTP client configuration, so the timeout test imports it, and fails within 5 s instead of hanging when the timeout is not applied. A 5xx is tested on each adapter through `MockRestServiceServer`. The timeouts are initial values, checked against the latency measured by hand (task 12a checklist). |
