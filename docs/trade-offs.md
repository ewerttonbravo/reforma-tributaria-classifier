# Trade-offs

Compromises made consciously and why. This document grows with each task.

Each compromise has a kind: a **design choice** would stay the same with more time; a **temporary** one has a planned removal.

| Area | Kind | Compromise | Why | Way out |
|---|---|---|---|---|
| Module boundaries | Design choice | Layering enforced by tests, not by the compiler | A single module keeps the build simple | Split into Maven modules if the codebase grows |
| Build time | Design choice | PIT runs in every `verify`, locally and in CI | A mutation gate that runs only on demand stops being run | Incremental analysis (`withHistory`) if the build gets slow |
| AI prompt size | Design choice | The AI receives all 164 `cClassTrib`, not only those linked to the product's NCM | The calculator offers no list by NCM (D5); checking each candidate would take 164 calls per product | Pre-filter with `ncm-aplicavel` or the calculator's annex tables if cost or accuracy demand it |
| Calculator build | Temporary | The calculator is built with `-Dmaven.compiler.proc=full`, a flag its README does not mention | Release `1.6.1` targets Java 21 and does not build on JDK 25 without it (D4) | Drop the flag when a pinned release builds on JDK 25 as published |
| CSV format | Design choice | Fields are split on `;` with no quoting, so a description cannot contain `;` | The catalog is fictitious and one split keeps the parser small; a line with an extra `;` is rejected, never misread | An RFC 4180 parser in the adapter if real catalogs need it |
| Durability | Design choice | The local broker and the test broker keep one replica, so `acks=all` waits for the leader only | One machine runs the demo; three brokers would add nothing the tests can observe | Three brokers, replication factor 3 and `min.insync.replicas=2` in production |
| CSV encoding | Design choice | Only UTF-8 is read; a file saved as Windows-1252, the default of Excel in Brazil, fails with exit code 2 | Guessing the encoding could turn `Feijão` into `FeijÃ£o` without anyone noticing, and the description is what the AI classifies | An `--encoding` option if real catalogs need it |
| Calculator failure type | Temporary | Apart from `CalculatorUnavailable` (D23), the candidates, legal basis and calculation ports fail with Spring's `RestClientResponseException` for a 4xx (or `RestClientException` for an answer that does not parse, such as an unknown `estadoItem`, and a `NoSuchElementException` for a calculation answer with no item), or a `NullPointerException` for a missing body, `cClassTrib` array or code, or a calculation answer missing its state, errors or total, which the application layer cannot name | Asking again gives the same answer, so the retry leaves them out (D24), and none is handled differently from another until task 13 sends a failure to review | Task 13 sends them to `produtos-revisao` with their cause; a failure type in the ports if review needs to tell them apart |
| AI confidence | Design choice | The confidence threshold trusts the confidence the AI declares, which is not calibrated: a wrong suggestion can come with high confidence | The official list catches unofficial codes and the calculator catches a `cClassTrib` not linked to the NCM (D5); the threshold only filters the answers the AI itself doubts | Calibrate the threshold against the accountant's review decisions once there are enough of them |
| AI client footprint | Design choice | The Anthropic SDK brings OkHttp, Jackson 2, Kotlin and OpenTelemetry next to Spring's Jackson 3 | The official SDK gives typed requests, structured output from a record and typed errors; writing the Messages API by hand would repeat that | Call the Messages API with `RestClient` if the footprint ever costs more than it saves |
| Missing legal basis | Design choice | An accepted suggestion of a `cClassTrib` with no published legal basis (220001, 220002, 220003) reaches the accountant without a legal citation | The calculator publishes none for them (D13); sending them to review would flag a choice the AI did not get wrong | Send them to review if accountants ask for a citation on every classification |
| Failed classification | Temporary | A product whose classification fails for good (a permanent AI or calculator error, a `FALHA_TECNICA`, a database error, a failed send) or after its retries run out (D24), or a record on `produtos` that is not a product's JSON or lacks its NCM or description, is logged and skipped: it reaches neither output topic | Sending to review is task 13; until then a skip keeps the partition moving | Task 13 sends an exhausted or permanent failure and a malformed record to `produtos-revisao` |
| Official list freshness | Design choice | Each calculator adapter reads the official list and the legal bases once per date, so a calculator updated during the day is seen only on the next date or after a restart | The official tables are published by date, so a date's lists are not expected to change; upgrading the calculator is a deliberate step, since D4 pins its release, and restarting the service can be part of it | An expiry on the cached date, or a restart when the calculator is upgraded |
| Operation location | Design choice | Every product is calculated as an operation in the one municipality of the configuration, São Paulo by default | The products CSV has no location, and the classification does not depend on it; the IBS shares of the state and the municipality do | A location per company or per product in the CSV if real operations span several municipalities |
| Nominal rates | Design choice | Every calculation from 2027 on uses the one set of nominal rates of the configuration, so its amounts are a simulation, flagged as such, and not the law's | The calculator holds no rates after 2026 and requires them from 2027 (D18); the reference rates are yet to be set, and the IBS share grows each year from 2029 | A set per year in the configuration, or the calculator's own rates once a release publishes them |
| Simulated immunity | Design choice | From 2027 a calculation under a CST with no CBS/IBS group, such as an immunity, is flagged simulated although its amounts are 0.00 whatever the rates | The adapter sends the rates for every CST; the calculator publishes no endpoint that says which CST has the group (D18) | Send the rates only for a CST with the group, if a release publishes which ones have it |
| At-least-once | Design choice | A service that dies after sending a product's result and before committing its offset classifies the product again: the result reaches the output topic twice, though the AI is paid once, since its suggestion is saved (D22) | Committing before sending would lose the product instead (D20); exactly once would need Kafka transactions on both the consumed offset and the sent result, and still not cover the call to the AI | A consumer of the output topics keeps the last result per product code |
| Stored suggestion age | Design choice | A saved suggestion is reused on any later day and never refreshed: a new calculator release, model or prompt does not reach a product already answered, a suggestion sent to review is not asked again, and the table grows with every new description, with no cleanup | The AI's answer depends on the description and NCM only (D11); the repeat is still checked against the official list of the day and calculated, so a code that left the list goes to review instead of standing (D22) | The model, prompt and calculator release in the key, or an expiry; meanwhile, deleting a product's row asks the AI again |
| Schema management | Design choice | `schema.sql` creates the suggestions table on every start, with no versioned migrations: changing a column would take a manual `ALTER` or a new database | One table, written once; a migration tool would add a dependency and its configuration for it (D21) | Flyway once the schema needs its first change |
| Local database credentials | Design choice | The local PostgreSQL user and password (`tax_classifier`) are written in `compose.yaml` and `application.yaml` | The database runs on the developer's machine and holds fictitious products only; `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD` override them | Credentials from a secret store in any shared environment |
| Stalled partitions | Design choice | While a record waits to be retried, every partition of its consumer waits too, up to 61 s per record, or about 3 min when the failure changes class (D24) | A blocking retry keeps a product's updates in order (scenario 5); retry topics would let a later update overtake one that waits | Retry topics with a check of each product's latest version, if the stall costs more than the order |
| Database and send without retry | Design choice | A failure of PostgreSQL or of the send to the output topic is not retried: the product is skipped, and if the AI had answered, its next read pays for it again | The application layer cannot tell a database error from a bug (D22), and neither failure was seen in the scenarios; retrying them would widen the retry to failures nobody measured | Name them as transient in the adapters, like D23, if they show up |
| Rate limit | Design choice | A 429 from the Claude API waits the same backoff as any unavailable AI, not the `retry-after` it carries | The backoff reaches 30 s, and the AI is called once per new product, so the demo does not reach the rate limit; reading the header would add it to the port | Carry `retry-after` in `AiUnavailable` and wait the longer of the two |
| Retry cost | Design choice | A Claude call that times out or loses its connection may still be billed, and its retry pays again | The SDK cannot tell a call that was billed from one never sent (D23); the slowest call measured took 7.6 s against a 60 s timeout | Fewer retries for an AI with no answer, if the bill shows it |
